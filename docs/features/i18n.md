# Overview

The GameShelf UI is internationalized with **English as the default locale**
and Polish as the optional alternative (ticket 7.2). The language is a
**per-user preference persisted server-side** (`users.language`), never a
per-device or per-session signal: it follows the account across devices, and
an unauthenticated visitor always sees English.

The pieces:

- a closed language set `['pl', 'en']` shared by the API validation, the wire
  contract, and the cookie;
- the `NEXT_LOCALE` `httpOnly` cookie, written by the API on login, first-run
  setup, and `PUT /settings/preferences`, cleared on logout and passive
  session expiry;
- per-request locale resolution in the web app (next-intl
  `getRequestConfig`) that reads the cookie and falls back to `en`;
- two typed message catalogs (`messages/pl.json` — the source of truth for the
  key set — and `messages/en.json`), kept in lockstep by a parity test;
- a custom ESLint rule that fails `npm run lint` on a newly hardcoded
  user-facing string.

Theme (dark/light) is covered by [Theme (light/dark/system)](/theme.md)
(ticket 7.3).

# Language set and persistence

`apps/api/src/i18n/language.ts` defines the closed set:

```ts
export const SUPPORTED_LANGUAGES = ['pl', 'en'] as const;
export const DEFAULT_LANGUAGE: Language = 'en';
```

- The `users.language` column (`VarChar(8)`, default `en` since migration
  `20261014070500_default_language_en`; the original
  `20261008071527_add_user_language` created it with a `pl` default) stores
  the preference.
- `PUT /settings/preferences` validates the body with `@IsIn(SUPPORTED_LANGUAGES)`,
  so a typo can never reach the database.
- Every read path coerces the stored value with `toLanguage()` (an invalid or
  legacy row falls back to `en`), so a corrupt value can never reach the
  cookie or a response body.

# NEXT_LOCALE cookie

`apps/api/src/i18n/locale-cookie.ts` is the bridge between the API (which owns
the per-user language) and the web app (which reads the cookie to pick the
catalog):

| Event                                   | Cookie action                                                                                                   |
| --------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `POST /auth/login`                      | set to the user's stored language (heals a stale/missing cookie — login is the one reliable server-render hook) |
| `POST /setup` (first account)           | set to the new account's language (`en`, the default)                                                           |
| `PUT /settings/preferences`             | re-set to the new language                                                                                      |
| `POST /auth/logout`                     | cleared                                                                                                         |
| passive session expiry (`SessionGuard`) | cleared                                                                                                         |

Flags: `httpOnly` (only the web app's server components read it, via
`cookies()`; the client-side switcher gets its value from server props, so
JavaScript never reads the cookie and it cannot leak), `SameSite=Lax`,
`path=/`, `maxAge` one year (a durable preference, not a session signal),
`secure` when `SESSION_COOKIE_SECURE` is set.

Clearing on logout/expiry matters on shared devices: without it the login
screen would render in the previous user's language; with the cookie gone the
web app falls back to the `en` default.

# Locale resolution (web)

`apps/web/src/i18n/` wires next-intl **without i18n routing**:

- `config.ts` — `LOCALES = ['pl', 'en']`, `DEFAULT_LOCALE = 'en'`,
  `LOCALE_COOKIE_NAME = 'NEXT_LOCALE'`; the set is closed and mirrors the
  API's `SUPPORTED_LANGUAGES`.
- `request.ts` — the `getRequestConfig` seam, linked from `next.config.mjs`
  via `createNextIntlPlugin('./src/i18n/request.ts')`. It reads the
  `NEXT_LOCALE` cookie per request, falls back to `en` on anything missing or
  invalid, and dynamically imports the matching catalog so the unused locale
  is never bundled into the other locale's build output. Reading the cookie
  makes the app request-dynamic, which is fine — every route is already
  `force-dynamic`.
- `app/layout.tsx` — `getLocale()`/`getMessages()` set `<html lang={locale}>`
  and feed `NextIntlClientProvider`, so client components (`useTranslations`)
  and server components (`getTranslations`, plus `generateMetadata` for the
  document title/description) resolve the same locale.

There are no locale-prefixed URLs (`/pl/…`, `/en/…`): the locale is a
cookie-driven rendering decision, and switching language is a preferences
mutation, not a navigation.

# Message catalogs

`apps/web/messages/pl.json` is the **source of truth for the key set**:
`src/i18n/messages.d.ts` augments next-intl's `AppConfig.Messages` with
`typeof pl`, so a key missing from `pl.json` is a **compile error** under
`tsc`, and a key missing from `en.json` is caught by the parity test
`apps/web/test/messages.test.mjs` (the same dotted key set in both
directions, every leaf a non-blank string, and the same ICU placeholders per
key in both catalogs).

Namespaces (one per screen/concern): `metadata`, `auth`, `nav`, `common`,
`settings`, `preferences`, `gameDatabases`, `catalog`, `loading`,
`catalogFilters`, `pagination`, `gameDetail`, `gameEdit`, `deleteGame`,
`reEnrich`, `manualAdd`, `import`, `importProgress`, `importAttention`,
`platforms`.

Client components use `useTranslations('ns')`; server components use
`getTranslations('ns')`. `src/i18n/translate.ts` exports `TranslatorFor<NS>`
so a `lib/*` helper can accept a fully typed translator for a namespace
without re-declaring its shape.

# ICU plurals

Counts use ICU plural syntax, and the two catalogs use **different plural
categories** — Polish has three (`one`/`few`/`many`/`other`), English two
(`one`/`other`):

```json
// pl.json
"showing": "Pokazuję {first}–{last} {total, plural, one {z # gry} few {z # gier} many {z # gier} other {z # gier}}"
// en.json
"showing": "Showing {first}–{last} of {total, plural, one {# game} other {# games}}"
```

The parity test compares the **placeholder names** per key (not the plural
category names), so the categories may differ while the required values must
match.

# Locale-aware formatting

Beyond the message catalogs, two formatters are locale-aware:

- **Dates** — `game-detail-view.tsx` formats `enrichedAt`/`createdAt`/
  `updatedAt` with next-intl's `getFormatter()` (`dateTime`,
  `dateStyle: 'medium'`, `timeStyle: 'short'`, `timeZone: 'UTC'`) so server
  and client text never disagree; `null` renders the translated "never" and
  an unparseable value the translated "unknown".
- **Sizes** — `lib/import/selection.ts#formatBytes` uses
  `Intl.NumberFormat(locale, …)` (the locale from `useLocale()`), so the
  decimal separator is `12,5 MB` in PL and `12.5 MB` in EN.

# Preferences API and switcher

- `GET /settings/preferences` → `{ language }` — the current user's stored
  preference (the shape is an object, not a bare string, so future
  preferences can be added without a breaking wire change).
- `PUT /settings/preferences` with `{ language: 'pl' | 'en' }` → persists
  `users.language` and **re-writes the `NEXT_LOCALE` cookie** on the response,
  so the next server render uses the new catalog.
- The web switcher is `components/preferences-form.tsx` on the `/settings`
  screen (the Preferences section above the LLM form): a `pl`/`en` select
  preselected from the server-fetched preference, a Save button (disabled
  while saving or when unchanged), `router.refresh()` after a successful PUT
  so the server components re-render in the new language, a `role="status"`
  saved note, and a `401` → `/login` redirect.

# Hardcoded-string guard

`apps/web/eslint-rules/no-hardcoded-strings.mjs` is a custom flat-config rule
(`gameshelf/no-hardcoded-strings`, enabled as `error` in
`apps/web/eslint.config.mjs` for `src/**/*.{ts,tsx}`) that makes a newly
hardcoded user-facing string **fail `npm run lint`** (the CI gate):

- flags `JSXText` containing letters, and string literals / static
  template-literal quasis in the guarded attributes `aria-label`,
  `aria-description`, `aria-placeholder`, `title`, `placeholder`, `alt`,
  `label`, `submitLabel`, `description`;
- does not flag dynamic expressions (`{t('…')}`, `{variable}` — the
  translator and server-provided values are not literals), non-user-facing
  attributes (`className`, `href`, `role`, `type`, `name`, `id`, `data-*`),
  elements marked `translate="no"` (or `translate={false}`), the brand
  `GameShelf`, and punctuation/whitespace/number-only values (`×`, `—`, `404`);
- its behavior is pinned by `apps/web/test/no-hardcoded-strings.test.mjs`
  (ESLint `Linter`, flat config).

Documented blind spots: strings returned from `lib/*` helpers, `ApiError`
internal messages, and server-provided text are outside JSX and not caught by
the rule; the parity test and the typed keys cover the catalogs, and the
helper literals were removed during the string extraction.

# Acceptance

- A fresh account (setup) renders the whole UI in English, with
  `NEXT_LOCALE=en` set.
- Switching to Polish on `/settings` re-renders the page in Polish and the
  choice persists across logout/login and across devices (it is the
  account's stored preference).
- Logout clears `NEXT_LOCALE`; the login screen renders in English.
- A hardcoded user-facing string in `apps/web/src` fails `npm run lint` with
  `gameshelf/no-hardcoded-strings`.
