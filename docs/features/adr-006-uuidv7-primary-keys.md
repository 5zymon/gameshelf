# Status

Accepted. Auto-increment integer primary keys are replaced by UUIDv7
`CHAR(36)` across the schema, foreign keys included.

# Context

- **MySQL 8.4 has no native UUIDv7.** The server's `UUID()` function returns a
  v1 UUID, and Prisma 7.10 with `@prisma/adapter-mariadb` has no server-side v7
  generator, so the ids have to be generated in the application.
- **Integer keys are enumerable.** `/games/<id>` exposes a sequential count of
  the library and lets anyone scan neighbouring rows.
- **Ordering is load-bearing.** The catalog's default sort, keyset paging
  (`id > cursor`) and the photo-import claim
  (`ORDER BY id LIMIT 1 … FOR UPDATE SKIP LOCKED`, ADR-005) all assume
  ascending id = creation order.
- **One raw-SQL insert bypasses Prisma.** `createFirstUser` writes through
  `$executeRaw`, where a Prisma-generated default never applies.
- **The data is disposable now.** The dev and test databases hold nothing worth
  keeping, so a wiping migration is the cheapest it will ever be; once a real
  library exists, a row-preserving migration would be a much bigger job.

# Decision

**D1 — ids are generated in the app by Prisma: `@default(uuid(7))`.** MySQL
cannot produce a v7, so the schema asks Prisma for one. Prisma 7.10's runtime
bundles the `uuid` library's monotonic v7 (a per-millisecond sequence counter,
lowercase output), so ids generated by one process sort in creation order.

**D2 — the one raw-SQL insert generates its id with a local helper.**
`createFirstUser` supplies `id` from `apps/api/src/common/uuid-v7.ts`
(`uuidv7()`, RFC 9562 built on `node:crypto`). No new dependency:
`crypto.randomUUIDv7` only exists from Node 26.1 (`engines` is `>=24 <25`) and
`uuid@14` is ESM-only.

**D3 — columns are `CHAR(36)` (`@db.Char(36)`), not `BINARY(16)`.** Prisma maps
`String` to `CHAR` natively; `BINARY(16)` would force `Bytes` types and
conversions through every layer. The size cost does not matter at this scale.

**D4 — the two singleton tables keep `Int @id` fixed at 1.** `llm_settings` and
`import_queue_state` drop `AUTO_INCREMENT` but not their integer key: the key is
a constant that is never exposed, so a UUID adds nothing, and keeping it
preserves the saved LLM base URL and encrypted key through the migration.
Switching them to UUIDs later is a four-file change.

**D5 — `sessions.id` stays as is.** It is an HMAC string, not a row key anyone
references; only `sessions.user_id` becomes `CHAR(36)`.

**D6 — every id input is validated with `@IsUUID('7')`.** A malformed or
non-v7 id is a `400`; a well-formed but unknown id is a `404`. Swagger
documents every id with `format: 'uuid'` and a v7 example.
`validator@13.15.35` supports version `'7'`.

**D7 — `ORDER BY id`, `orderBy: { id }` and the `id > cursor` paging stay.**
Lowercase UUIDv7 strings sort lexicographically in creation order, so the
catalog's `id ASC` tiebreaker, its keyset paging and the queue's oldest-first
claim keep working unchanged.

**D8 — one new append-only migration.**
`20261013125522_uuidv7_primary_keys` deletes the rows of the non-singleton
tables (existing integer ids cannot become valid UUIDv7s) and then runs
Prisma's generated `ALTER`s: drop the eight foreign keys, `DROP PRIMARY KEY` +
`MODIFY id CHAR(36) NOT NULL` + `ADD PRIMARY KEY (id)` per table, re-add the
foreign keys with their original `ON DELETE` rules (CASCADE, except
`games.platform_id` RESTRICT and `recognized_items.game_id` SET NULL). Old
migrations are not squashed, so `migrate deploy` — which the test-DB setup
uses — keeps working.

# Consequences

- **The migration wipes keyed data.** Every game, platform, alias, import job,
  recognized/unrecognized item, image, video, session and user row is deleted;
  only `llm_settings` and `import_queue_state` keep their rows. It runs on
  every database `npm run db:deploy` touches, so a self-hosted instance with a
  real library would need a row-preserving migration instead.
- **MySQL DDL is not transactional.** A migration that fails halfway leaves the
  schema inconsistent; the recovery is `prisma migrate reset --force` and a
  re-seed (dev).
- **400 vs 404.** A malformed id (a non-UUID or a non-v7 UUID, e.g. a v4) is a
  `400`; a well-formed but unknown id is a `404`. `/games/999999` used to be a
  `404` and is now a `400`. The web app validates before fetching
  (`isUuidV7`), so `/games/<garbage>` is its own 404 page rather than an API
  error.
- **Ordering is creation order, with one caveat.** UUIDv7 is strictly
  increasing within one process; across processes in the same millisecond the
  order is random. Only ties are affected (default catalog sort, simultaneous
  queue claims), which is acceptable.
- **Case.** `@IsUUID('7')` accepts uppercase; lookups still match because the
  table collation is case-insensitive, and responses always return the stored
  lowercase. The web helper lowercases platform ids before de-duplicating.
- **Raw SQL must supply ids.** Prisma's generated default does not apply to raw
  SQL, so any future raw `INSERT` must generate its id with
  `common/uuid-v7.ts`; the schema header comment and the helper's docstring say
  so.
- **Keys got bigger.** `CHAR(36) utf8mb4` keys are larger than `INT`, but
  inserts stay roughly in order (v7 is time-ordered), and id enumeration is
  gone — a fair trade at home-library scale.
