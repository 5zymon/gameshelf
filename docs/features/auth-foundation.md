# Overview

The auth foundation implements ADR-004 at the service layer: passwords are
hashed with Argon2id, sessions are stored server-side in MySQL, and every
credential comes from the environment. There is **no JWT dependency** — sessions are opaque random tokens held in the
database, so revocation is immediate and no token payload can be forged.

This ticket ships services and configuration only. The HTTP
signup/login/logout endpoints, cookie handling, and the global guard are
provided by the [Auth API](/auth-api.md) on top of these services.

# Password hashing

`PasswordService` wraps `argon2`:

- `hash(plain)` returns an **Argon2id** encoded hash (`$argon2id$…`). The salt
  is generated by the library and embedded in the encoded string; the hash is
  never reversible.
- `verify(hash, plain)` returns `true` only for the matching password. A
  malformed hash is caught and returns `false` rather than throwing.

`UsersService.createUser` normalizes the email (trim + lowercase), rejects a
blank email or empty password with `400`, hashes the password, and inserts the
row. A duplicate email (unique constraint `users.email`, Prisma `P2002`) maps
to `409`. The returned `CreatedUser` carries `id`, `email`, and `createdAt`
— **never** `passwordHash`.

`UsersService.createFirstUser` shares the same `prepareUser()` normalization,
validation, and hashing path and additionally inserts only while `users` is
empty (atomic `INSERT … SELECT … WHERE NOT EXISTS`), backing the one-time
bootstrap documented in [First-run Setup](/first-run-setup.md). `hasAnyUser()`
reports whether any account exists.

# Session model

Sessions live in the `sessions` table:

| Column       | Type           | Notes                                |
| ------------ | -------------- | ------------------------------------ |
| `id`         | `VARCHAR(255)` | Primary key → indexed (acceptance)   |
| `user_id`    | `INTEGER`      | FK → `users.id`, `ON DELETE CASCADE` |
| `expires_at` | `DATETIME(3)`  | Finite expiry instant                |
| `created_at` | `DATETIME(3)`  | Defaults to `CURRENT_TIMESTAMP(3)`   |
| `user_agent` | `VARCHAR(255)` | Nullable request fingerprint         |

**Stored id is a digest, not the token.** `SessionsService.create` mints a
32-byte random token (`base64url`, 43 chars) and returns it to the caller. The
database stores only `HMAC-SHA256(SESSION_SECRET, token)` as `id` (64 hex
chars). `validate` recomputes the digest and looks up by it, so the cookie
token itself is never persisted and a database leak does not yield usable
session tokens.

# Expiry and cleanup

- `SESSION_TTL_MINUTES` is validated to an integer in `1..525600`
  (1 minute … 1 year). Missing/empty falls back to `10080` (7 days). A
  non-positive, non-integer, or out-of-range value is rejected — there is
  **no "never" option**.
- `SessionsService.validate(token)` loads the row, returns `null` and deletes
  the row if it is expired, otherwise **slides** `expiresAt` forward to
  `now + ttl` and returns `{ userId, expiresAt }`.
- `SessionCleanupService.cleanup()` runs on `@Interval` every hour
  (`SESSION_CLEANUP_INTERVAL_MS`) and calls
  `SessionsService.cleanupExpired()`, which deletes all rows with
  `expires_at < now` and logs the removed count. `revoke(token)` deletes by
  digest and is idempotent.

# Configuration

`loadAuthConfig(ConfigService)` produces the injected `AUTH_CONFIG`:

| Env var               | Required | Rule                                                       |
| --------------------- | -------- | ---------------------------------------------------------- |
| `SESSION_SECRET`      | yes      | ≥ 32 characters; HMAC-SHA256 key for the stored session id |
| `SESSION_TTL_MINUTES` | no       | Integer `1..525600`, default `10080`                       |

Secrets come **only** from environment variables
(`ConfigService.getOrThrow('SESSION_SECRET')`); no default secret is baked
into the code and no `.env` file is committed. The cleanup cadence is a code
constant, not env-driven.

# Service surface

`AuthModule` provides and exports `AUTH_CONFIG`, `PasswordService`,
`UsersService`, and `SessionsService`; `SessionCleanupService` is provided
internally (scheduled). `AppModule` imports `ScheduleModule.forRoot()` and
`AuthModule`.

| Service                 | Methods                                                                                                  |
| ----------------------- | -------------------------------------------------------------------------------------------------------- |
| `PasswordService`       | `hash(plain)`, `verify(hash, plain)`                                                                     |
| `UsersService`          | `createUser({ email, password })`, `createFirstUser({ email, password })`, `hasAnyUser()`                |
| `SessionsService`       | `create(userId, { userAgent?, now? })`, `validate(token, now?)`, `revoke(token)`, `cleanupExpired(now?)` |
| `SessionCleanupService` | `cleanup()` (`@Interval(3600000)`)                                                                       |

# Out of scope

- HTTP surface: implemented by the [Auth API](/auth-api.md) (`POST /auth/login`,
  `POST /auth/logout`, `GET /auth/me`, cookies, and the global guard).
- Password policy and strength rules.
- Roles and permissions (single permission level — decision #14).
- Frontend auth UI.
